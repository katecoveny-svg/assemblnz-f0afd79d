03 · look underneath

what Assembl actually needs.

Not Nectar's whole data warehouse. Start with the events and tools required for the two agents to do useful work. Everything else is earned by a specific use case.

Applicant agent · minimum

  • application/session reference
  • current journey state
  • quote fields Nectar already exposes
  • missing-information flags
  • signing / funding status
  • customer communication permission

Growth operator · minimum

  • Google / Meta / Microsoft read access
  • analytics + landing events
  • campaign/source identifiers on applications
  • assessable / approved / funded outcome events
  • experiment results
  • write access only for explicitly allowed actions

Authority model

  • read broadly enough to reason
  • prepare before acting
  • bounded changes can be pre-authorised
  • larger budget / creative changes require approval
  • compliance escalates to a person
  • every action leaves a receipt
Hard boundary: Assembl does not make Nectar's lending decision.

The decision engine and responsible lending/compliance framework stay authoritative. The applicant agent explains and resolves the journey around the decision. The growth operator learns from aggregate downstream states without turning approval into an advertising optimisation target that overrides compliance.
