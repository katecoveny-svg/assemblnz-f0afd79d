# Portable DO continuity · first review milestone

**Review prototype. Durable integration inactive.** This branch builds the phone-compatible `/do/continue` surface, a bounded task contract, an editable deterministic EA worksheet, a cookie-authenticated durable adapter and an independently executable SQL proposal. It does not yet prove authenticated cross-device continuity. No production schema, grants, feature flags, credentials, paid inference or external actions were changed.

## Objective and scope

Deliberately paste one request → review explicitly selected notes → consent to saving → keep one stable task ID → reopen the same owner/scope task → prepare and edit a result. Authority is preparation only. Personal and Work are distinct scopes; identity/scope changes clear the composer, selected notes, consent and result. Memory collection consent is not preparation/provider consent.

Files are limited to `apps/do/continuity/*`, `app/do/continue/*`, `app/api/do/continuity/*`, this proposal package and the isolated SQL test script. Provider/UI, memory and peer-scheduling owners retain their modules. No changes to Ask Assembl, scheduled responsibilities, native wrappers, extensions, shared preparation, or owner-review-only memory.

## State and truthful persistence

`waiting → needs_review → edited needs_review`; `cancelled`, `revoked` and permission `expired` stop preparation. Every edit/revoke/cancel checks the displayed revision. Repeat save uses the exact original UUID/payload without renewing consent. Changed payload with the same UUID fails. SQL preparation is a deterministic worksheet in one transaction; concurrent requests yield one committed revision. There is no hidden queue, background execution, model call or success receipt.

The explicit **fictional fixture** is browser-only. Local storage writes must succeed before the UI says saved. Failed writes and network transport errors never receive an online/durable label. Fixture reload/close/reopen retains its stable task and edited result only in that browser. Expired fixture content is cleared when reopened; a closed browser cannot run retention maintenance. This is not account-backed or secure multi-person storage; enter fictional test data only.

The durable adapter accepts a verified owner's cookie client, never a service-role key. SQL obtains `auth.uid()` and rejects anonymous users; it never trusts a body owner/clock/status/result for save. Private tables have RLS and no client access. Guarded RPCs are deliberately `SECURITY DEFINER` to keep direct write bypasses closed; public/anon/authenticated/service_role execute grants are revoked in the proposal. Inherited Supabase-style default ACLs are seeded in the isolated harness and explicitly revoked on every created object. Every function pins an empty search path and every task access filters owner + scope. All new RPC execute grants exist only inside the disposable test harness.

**Activation is hard closed** in `apps/do/continuity/activation.ts`, with a second independent database gate. The private `owner_access` table admits only an explicitly enabled owner + exact scope until a server-clock expiry. The proposal inserts no access rows and enables no owners. Clients cannot self-enrol or access this table; granting authenticated RPC execution alone does not enrol eligible accounts. Gates are checked again after locks and before preparation writes. Authenticated save/reload currently returns 503 and `durable:false`; guest returns 401. No memory fallback. `X-DO-Workspace` is a checked expectation, not authorisation. Stopping a request stops waiting on that device; it does not promise the server rolled back. Reopen after an uncertain acknowledgement before editing or cancelling. Same-ID retries prevent duplicate saves. PostgreSQL validates UTF-16 code units for every request/context/result text bound to match the web/Zod contract even on direct RPC calls.

## Consent and context

Only manually pasted and explicitly selected task notes are admitted, up to three 2,000-character entries plus a 4,000-character request. No memory reader is imported. Existing `owner_review_only` records remain inaccessible. No provider-memory bodies or refs enter fixture/peer handoffs/logs. Future scoped memory integration must use the memory owner's independently approved versioned consent and exact owner-private record references. Rejecting a suggestion or choosing a one-off option never creates a preference.

Current consent is **storage + inert worksheet only**, expires after 24 hours and does not grant OpenAI/TypeSafe transmission. Server wall time is captured after owner/row locks and rechecked before preparation commits. Revocation/cancellation clears selected notes and result. Seven-day retained content is hidden immediately at expiry and physically cleared by the proposed private maintenance hook. Content-free stable-ID sentinels remain until account deletion, so a day-100 or later retry cannot recreate consent. An owner is limited to 40 unexpired tasks, 256 KiB of stored request/context/result bytes and 2,048 lifetime stable IDs across both scopes. Owner mutations are serialised to enforce count and output-growth quotas atomically. **Approval decision:** retaining this bounded, owner-private ID/scope/revision/timestamp/status metadata until account deletion permanently prevents late retry enrolment; after 2,048 accepted task IDs, this owner can reopen/edit admissible existing work but cannot create new IDs. The UI reports “Task storage is full. No new work saved.” There is no automatic ID deletion, quota reset, renewed consent or silent fallback. Review the product/privacy trade-off before activation; this PR does not assert the lifetime-cap policy is approved. No cron is installed. Maintenance configuration and policy review are required before enabling durable storage.

## Exact enablement needs

1. Independently review `schema-proposal.sql` at its recorded SHA-256 and this contract. It is outside automatic migrations. Do not apply it to production from this task.
2. Install the exact proposal in an approved isolated Supabase environment with actual Auth. Review the function owner, security-definer checks, RLS, default privileges and schema exposure. Run the SQL harness/advisors and actual cookie/RPC tests. No new application credentials are needed; the existing publishable-key SSR client is the intended transport.
3. Separately approve **authenticated-only EXECUTE** on `do_continuity_read(text,uuid)` and `do_continuity_mutate(jsonb)`. Keep `anon`, `PUBLIC`, `service_role`, direct private table access and private helper execution denied. No authenticated table grants are needed. Confirm public RPC exposure/schema cache in the chosen environment. A trusted administrator must then separately enrol each reviewed canary owner + scope with an expiring private access row. No owner is pre-enabled by this proposal, and disabling/expiring its row closes both reads and mutations; account-data erasure/retention remains the trusted maintenance/account-deletion path.
4. Approve and configure the private `prune()` maintenance path, its maximum retention delay, account-delete cascade and bounded lifetime sentinel policy. Confirm physical content deletion with expired fictional rows and rejection of a late same-ID retry. No scheduling or cron is added here.
5. Root review must approve changing the closed activation constant for that environment. Deploy an isolated preview, then sign the same owner in on an actual phone/session A and independent desktop/session B. Save on A, reopen by the same task ID on B, edit/reopen on A, test owner B denial, expiry, revocation, stale revisions and an acknowledgement-loss retry. Only then label authenticated cross-device continuity proven. Preview Auth/site/cookie configuration may need the existing project's approved redirect origin; no new grants are assumed.
6. Model drafting is a separate adapter stage. Reuse the provider owner's reviewed Astra 6 + TypeSafe consent, entitlement and durable cost/admission gate. This proposal's atomic deterministic preparation must not be replaced with network inference inside a DB transaction. Paid/remote executor work requires a reviewed durable claim/cancellation/uncertain-outcome design, not a silent fallback.

## ChatGPT/local execution research boundary

The task reviewed [Sign in with ChatGPT for eligible open-source apps](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), and [Codex app-server](https://learn.chatgpt.com/docs/app-server). Eligible personal local/open-source plan inference does not automatically authorise a commercial hosted DO service. Identity login, plan inference, local tool permission and ChatGPT memory access are separate. Preview restrictions include computer use, hosted MCP, audio, image generation, background mode and hosted conversation storage. App-server remains experimental; legacy authentication is not an approved commercial hosted transport. This branch adds no subscription adapter, token reading, token relay, native service or assumed model entitlement. API-funded Astra and external TypeSafe costs remain separate.

Supabase sources checked: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [RPC](https://supabase.com/docs/reference/javascript/rpc), [explicit API exposure change](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically), and [PostgreSQL minor-release changes](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes). This proposal does not use the affected extensions/operators. Existing production schema was not queried or changed.
