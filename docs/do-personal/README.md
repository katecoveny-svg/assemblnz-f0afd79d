# Personal DO persistence foundation — review build

Extends the existing responsibilities/runs/worker primitives. Existing daily preparation uses saved responsibility notes, seven-day permission, locked claims, hourly/account caps, revision invalidation, interrupted-run recovery and review receipts. No second scheduler or job store is introduced.

Optional account memory is off unless `DO_PERSONAL_MEMORY_ENABLED=true`. The proposed table/RPCs must exist before enabling; missing storage or purge fails closed (503). The new endpoint is `/api/do/personal/memory`: guest GET returns a storage-free contract; authenticated POST requires same origin and server-verified owner. No external account link is required. Writes are validated again in the service. The new `reviewQueue` on the existing personal endpoint projects next-run, permission, worker health and draft receipts. Review acknowledges a draft; it never authorizes external effects.

Memory is owner-entered, self-only, non-sensitive context, with explicit consent/notice version, observation and review dates, bounded text and 7/30/90-day retention. Edit uses an expected revision; pause disables the record; delete erases its body. Content-free UUID/revision tombstones prevent stale requests from restoring deleted or expired content. New context after deletion requires a fresh UUID. Purge removes expired bodies on each memory GET; expired data is excluded from reads/RLS. CAS also checks stored expiry under lock and atomically erases expired content before rejecting renewal. Absent-ID deletion fails; it never claims to have erased a record. **A scheduled purge, tombstone lifecycle and backup retention must be reviewed before activation:** lazy cleanup does not guarantee physical deletion by the expiry instant. The service-only batch RPC uses the expiry index and locks at most 100 rows; a scheduled caller must monitor purged counts, failures and oldest overdue expiry. Content-free owner/UUID/revision metadata currently lasts until account deletion to block stale resurrection. Its duration and abuse/storage cap need review separately from context-body retention. Database content deletion makes no claim to erase backups.

Memory is `owner_review_only`; it is not included in model prompts, calls, adapter input or background jobs. There is no provider-memory sharing consent in this phase. Existing explicitly saved responsibility notes retain their separate drafting consent. Memory cannot expand roles or permissions. Self-only and non-sensitive declarations are user attestations, not semantic guarantees about free text; the off-by-default feature requires privacy review before a collection UI is wired.

Family contract accepts only fictional generic aliases for a child, adult or supporter, with owner-only visibility and no authority. No actual family data, child accounts, school/health ingestion, family sharing, representative permission, sending, booking, payments or medical decisions are implemented. Family relationship is never blanket consent. The initial safeguards follow [OPC IPP3A guidance](https://www.privacy.org.nz/resources-and-learning/a-z-topics/ipp3a/), [child information guidance](https://www.privacy.org.nz/resources-and-learning/knowledge-base/view/1/) and [AI privacy guidance](https://www.privacy.org.nz/resources-and-learning/a-z-topics/ai/); they are not legal compliance certification. IPPs 1–3/3A, 5–10 apply to collection/purpose, optionality, access/correction, provenance and retention. No real personal or Māori identity/taonga data is used in proof fixtures.

`schema-review.sql` is a proposal outside migration discovery. Schema owner owns review and migration generation; nothing is applied. Local proof is `node scripts/test-do-memory-sql.cjs`, using pinned PGlite in /tmp; `DO_PROOF_POSTGRES=true` uses the isolated local PostgreSQL 17 test container on 127.0.0.1:55437 and additionally tests separate-session insert/CAS/purge races; it tests actual database close/reopen, retry/CAS, owner RLS, service-only writes, interrupted-job recovery, pause, expiry and deletion. Existing `scripts/test-do-personal-sql.cjs` verifies responsibility invariants. Unit/API tests use fictional fixtures only.

Rollback: keep memory flag off and remove additive endpoint/projection if needed; original job tables are unchanged. Before production: review/generate the unapplied migration, validate policies/advisors on a disposable branch, finish retention/notification/representative design, obtain the root activation sequence and verify worker runtime. Heartbeat alone is never proof that a specific draft completed or that live availability was checked.
