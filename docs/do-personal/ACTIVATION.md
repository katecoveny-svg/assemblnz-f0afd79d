# Optional memory activation gates — proposed, not scheduled

No schema, cron, feature flag or production maintenance is activated by this PR. The existing responsibility scheduler remains unchanged. `maintainPersonalMemory` is a tested service-only callable, separately off behind `DO_PERSONAL_MEMORY_PURGE_ENABLED`; collection remains off behind `DO_PERSONAL_MEMORY_ENABLED`. Keeping cleanup separately gated allows collection to be paused while expiry cleanup continues.

1. Schema owner reviews `schema-review.sql`, generates an unapplied migration through the standard workflow and proves it on an isolated database. Confirm owner SELECT RLS, revoked client writes/RPCs, expiry/index predicates, CAS after locks, anonymous denial, tombstone ABA, monitoring and restore behaviour. Production application still follows root release sequencing with Supabase autoproduction deployment off.
2. Before collecting live self context, complete privacy impact and collection-notice review, including intended recipients/processing location, access/correction and retention. Self-only declarations are attestations, not reliable free-text sensitivity classification. Family/child/supporter collection and representatives need a separate IPP3A design; this release provides fictional family preview metadata only.
3. An authenticated trusted maintenance endpoint/scheduler must be implemented and verified before activation. Do not wire the callable into public routes. Proposed cadence: hourly with existing worker-compatible operations; no new cron registration here. Each invocation calls at most three batches of 100 rows, starts no new batch after 15 seconds, aborts each batch request after five seconds, and bounds the monitoring request to two seconds. The database uses row locks/SKIP LOCKED and an expiry index. Before activation, verify effective database-side statement and lock timeouts in the actual service/PostgREST session; client aborts alone do not bound SQL execution. Use a disposable lock-wait/slow-query test and confirm cancellation before accepting the run budget. An aborted HTTP request may still commit; counts describe confirmed responses only. Failed calls are not immediately retried. Another invocation is safe because tombstoned rows are excluded.
4. Monitoring records only status, last attempt/completion and confirmed count. Health reads sample at most 1001 overdue rows and oldest overdue expiry; no owner/record IDs or content. Alert on every failed/deadline outcome, more than 90 minutes without a valid attempt, oldest overdue body more than 75 minutes old, and persistent backlog. Proposed target: expired content excluded from reads immediately; active-database bodies removed within 75 minutes under verified capacity. This is a release target, not a current guarantee. Capacity/load proof must show the hourly bounded worker drains expected peak expirations. If it cannot, reduce collection volume or explicitly approve a different cadence/capacity before collecting.
5. On alerts, disable new collection while preserving cleanup; do not expand batch limits silently. Inspect aggregate telemetry/query latency, restore the worker, then verify old bodies are gone and the oldest-overdue metric is clear. A failed monitoring write makes operational health unverified even when the previous database snapshot is recent. The eventual scheduler/endpoint must alert independently through its infrastructure error monitoring and failed-run status; do not rely on the same unavailable database to record that failure. Overall readiness combines the latest scheduler outcome with the aggregate database snapshot. Test this independent failure path before activation. Never infer deletion from worker heartbeat or a scheduled time alone.
6. Content-free owner/UUID/revision tombstones currently persist until account deletion. Agree separate metadata retention, storage/abuse limits and rate limits before activation. Do not delete tombstones without a generation/version replacement that prevents stale creates from resurrecting content. Thirty live records is not a bound on tombstone growth.
7. Verify actual backup/PITR retention, access controls, restore procedure and deletion limitations with the operational owner. No claim of backup erasure is made. Keep collection inactive and user reads unavailable during restoration; run expiry cleanup to completion, test tombstones/revisions and owner RLS, and verify no restored expired record is served before reopening. Deletion of active data is not a backup deletion receipt.
8. Root approves the reviewed migration sequence and canary activation only after these gates, complete exact-head CI/build and privacy/operational review. Verify canary save/edit/conflict/pause/review/delete/expiry and worker monitoring with fictional fixtures before live collection. Roll back by disabling collection; preserve cleanup, tombstones and monitoring. No external sends, bookings, payments, sensitive sharing or medical decisions are enabled.

Tests prove bounded runner, deadline/failure behaviour and health fail-closed states; server mocks verify inactive mode and aggregate monitoring. Isolated PostgreSQL proof verifies bounded SQL purge, monitoring access/shape, expiry/purge/CAS races and lock waits. These checks do not prove that a production scheduler exists, meets its target or that backups have been erased.
