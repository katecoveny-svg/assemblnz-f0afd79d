# Optional provider context — inactive contract

This extends the existing optional-memory and responsibility foundations. Collection remains `owner_review_only`. It does not enable provider context. A durable server adapter and SQL review proposal are provided, but no route, UI, applied migration, job schedule or provider call installs them. `DO_PROVIDER_MEMORY_ENABLED` is off by default and must remain off pending activation review.

`memory-use.ts` defines a separate versioned consent naming OpenAI and TypeSafe, exact selected record revisions (maximum eight, 6,000 characters combined), and one scope: assistant or a named responsibility plus its revision. Consent lasts at most seven days and cannot outlast any selected record. Records must be explicitly confirmed owner-entered self goals, preferences or constraints. No family, child, supporter, health or third-party records, inferred preferences, rejected suggestions or one-off decisions enter this contract. Existing collection records are rejected; a future owner-reviewed promotion must create separate confirmed provider context with its own retention choice, never silently mutate collection consent.

`memory-use-server.ts` exposes `readProviderMemory(store, authenticatedOwnerId, scope, consentId, clock?)` and `recheckProviderMemory(store, authenticatedOwnerId, scope, previousBundle, clock?)`. The trusted clock is sampled after awaited snapshot and scope checks, including during rechecks. Missing storage fails closed. All escaped storage/schema errors become content-free `MemoryUseError` codes. The adapter retrieves consent and selected records in a consistent owner-filtered snapshot; `scopeIsCurrent` verifies the responsibility's owner, active consent, revision and pause state. Assistant scope verifies a current authenticated non-anonymous owner. Never take owner ID from request JSON. Do not log record bodies, identifiers or validation payloads.

Provider orchestration must recheck immediately before **each** OpenAI and TypeSafe dispatch and before storing/showing output. For context-derived jobs, `publishPreparedWork` is the mandatory atomic publication RPC: it locks the existing responsibility/run, checks current context, consent and policy revisions/expiry, then stores output and prepared receipt in one transaction through the existing finish primitive. Do not call ordinary job finish and add a ledger receipt later. Independent request consent, provider budget and policy checks remain required. Revocation/edit/deletion/pause while a request is in flight discards its output; revocation cannot recall already-dispatched text. Never treat a recheck as an atomic lock across a network request. Bundle `data` is untrusted structured JSON, never system instructions. No confidence value authorises actions or verifies facts. Action authority remains `none`.

References contain only record ID/revision, observed/expiry times, consent ID/revision and scope. Keep them owner-private with the same retention as the prepared work; do not put them in public receipts, telemetry, portable fixture pages or peer EA handoffs. Portable continuity needs its own explicit context selection consent; no access to `owner_review_only` material. Clear ephemeral context on logout or owner switch. Peer scheduling receives no private memory bodies or references.

`preparation-controls.ts` adds deterministic eligibility for pause, local quiet hours, exact novelty keys, dismissal and elapsed-time cooldown. Derive keys from purpose/source revision, never private text. Equal quiet hours disable the interval. Dismissal suppresses work and never creates a durable preference. The SQL reservation reuses an existing owned running job, responsibility revision, provider consent and policy revision under an owner advisory lock. It inserts a unique owner/novelty key exactly once. `false` never authorises redispatch; after timeout/crash, the worker must query/review the reservation and mark uncertain work failed, rather than repeating paid calls. A new key remains subject to cooldown. SQL conservatively suppresses any previously reserved exact key, even after dismissal expiry; changing a source revision creates a new key. Preserve existing responsibility retry, cancellation and review-queue receipt rules; outputs are unsent prepared drafts. No claim of always-on monitoring follows from these contracts.

`memory-use-storage.ts` supplies the inactive Supabase adapter: `createProviderMemoryStore`, `changeProviderContext`, `changeProviderConsent`, `readProviderContextReview`, `changePreparationPolicy`, `reservePreparedWork`, `readPreparedWorkReservation`, `publishPreparedWork`, `changePreparedWorkState`. The state setter supports only failure/dismissal; only atomic publication creates a prepared receipt. Strict owner-free mutation inputs require self-only/non-sensitive confirmation, then a separate explicit versioned OpenAI+TypeSafe consent. No automatic copy from collection memory exists. A future authenticated same-origin review API must supply server-verified owner identity. Every RPC has a five-second client abort, which is not a guarantee of SQL cancellation.

The **unapplied**, outside-migrations proposal [provider-memory-schema.sql](./provider-memory-schema.sql) implements service-only owner-bound RPCs, RLS without client policies, CAS, immutable deletion/revocation tombstones, consistent retrieval, 30 active contexts/consents, 7/30/90-day context retention and account-deletion cascades. SQL uses the same UTF-16 length limits as JavaScript, normalises UUID selection identity, and rejects non-finite timestamps. The content-free reservation ledger is capped at 1,000 records per owner and one reservation per existing run; it survives individual job deletion and fails closed at its cap. Metadata retention/abuse controls and safe pruning remain activation gates. No grant or existing role permission expands.

Context edits/deletion and consent edits/revocation cancel linked jobs and remove their context-derived output/evidence. Reservation expiry is capped at consent expiry. `do_provider_context_expire(33)` removes at most 99 context/consent/derived-output bodies per call (33 per category). It must be integrated with monitored maintenance, backlog/oldest-expiry health and infrastructure alerts before activation; this PR does not register a scheduler. Existing cleanup, database statement/lock timeouts, backup/PITR quarantine and activation gates in [ACTIVATION.md](./ACTIVATION.md) remain required. Root sequences schema review, authenticated UI consent/review, provider integration, operations and activation. No Luna API or new provider permit system is introduced.

The proposal adds `provider_context_expires_at` to existing runs and narrows their existing owner-read RLS policy. `personalState` now reads runs with the authenticated cookie client, preserving the expiry boundary even when memory collection is paused; the service-role client remains for tasks/worker metadata. Expired derived rows (both output and evidence) disappear immediately at read time, while bounded cleanup erases their stored bodies later. No new role permission is granted. Any future service-role run reader must enforce the same expiry filter; service role bypasses RLS. Context/consent CAS samples wall-clock time again after output invalidation, which can block on a worker-held run row.

Proof: synthetic unit tests cover owner/purpose/revision/expiry/revocation, delayed-read expiry crossing, safe errors, absent storage, stale consent, collection-only rejection, injection as data, deterministic deduplication, dismissal, pause, cooldown and NZ DST quiet hours. `scripts/test-do-provider-memory-sql.cjs` tests actual schema behavior with PGlite disk reopen, plus PostgreSQL separate-worker reservation and optional actual process restart (`DO_PROOF_POSTGRES=true DO_PROOF_RESTART_POSTGRES=true`, only the named disposable localhost container). No provider, production database or real personal information is used. Hosted deployment, operational load/backlog and UI/provider publication integration proof remain outstanding.
