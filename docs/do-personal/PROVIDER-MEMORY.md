# Optional provider context — inactive contract

This extends the existing optional-memory and responsibility foundations. Collection remains `owner_review_only`. It does not enable provider context. No live adapter, route, UI, migration, job schedule, provider call or feature flag is added in this stage.

`memory-use.ts` defines a separate versioned consent naming OpenAI and TypeSafe, exact selected record revisions (maximum eight, 6,000 characters combined), and one scope: assistant or a named responsibility plus its revision. Consent lasts at most seven days and cannot outlast any selected record. Records must be explicitly confirmed owner-entered self goals, preferences or constraints. No family, child, supporter, health or third-party records, inferred preferences, rejected suggestions or one-off decisions enter this contract. Existing collection records are rejected; a future owner-reviewed promotion must create separate confirmed provider context with its own retention choice, never silently mutate collection consent.

`memory-use-server.ts` exposes `readProviderMemory(store, authenticatedOwnerId, scope, consentId, now)` and `recheckProviderMemory(store, authenticatedOwnerId, scope, previousBundle, now)`. A missing adapter fails closed. The adapter must retrieve consent and selected records in a consistent owner-filtered snapshot; `scopeIsCurrent` must verify the responsibility's owner, active consent, revision and pause state. Assistant scope must verify a current authenticated non-anonymous owner. Never take owner ID from request JSON. Store errors must become generic unavailable responses; do not log record bodies, identifiers or validation payloads.

Provider orchestration must recheck immediately before **each** OpenAI and TypeSafe dispatch and before storing/showing output. Independent request consent, provider budget and policy checks remain required. Revocation/edit/deletion/pause while a request is in flight discards its output; revocation cannot recall already-dispatched text. Never treat a recheck as an atomic lock across a network request. Bundle `data` is untrusted structured JSON, never system instructions. No confidence value authorises actions or verifies facts. Action authority remains `none`.

References contain only record ID/revision, observed/expiry times, consent ID/revision and scope. Keep them owner-private with the same retention as the prepared work; do not put them in public receipts, telemetry, portable fixture pages or peer EA handoffs. Portable continuity needs its own explicit context selection consent; no access to `owner_review_only` material. Clear ephemeral context on logout or owner switch. Peer scheduling receives no private memory bodies or references.

`preparation-controls.ts` adds deterministic eligibility for pause, local quiet hours, exact novelty keys, dismissal and elapsed-time cooldown. Derive keys from purpose/source revision, never private text. Equal quiet hours disable the interval. Dismissal suppresses work and never creates a durable preference. Persist history owner-scoped and reserve novelty keys transactionally with job claims: this pure evaluator alone cannot guarantee cross-worker idempotency. Preserve existing responsibility revision, retry, cancellation and review-queue receipt rules; outputs are unsent prepared drafts. No claim of always-on monitoring follows from these contracts.

Schema owner must design an **unapplied** proposal for consent/confirmed context/history, with owner predicates, RLS, service-only CAS, immutable deletion tombstones, owner deletion cascade, explicit 7/30/90-day context retention and consent revocation. Existing cleanup, backup/PITR quarantine and activation gates in [ACTIVATION.md](./ACTIVATION.md) remain required. This PR intentionally does not invent a second deployed memory store. Root sequences schema review, operational proof, UI consent and provider integration before any activation.

Proof: synthetic unit tests cover owner/purpose/revision/expiry/revocation, absent storage, stale consent, collection-only rejection, injection as data, deterministic deduplication, dismissal, pause, cooldown and NZ DST quiet hours. No provider, production database or real personal information is used. Database restart/concurrency/idempotency proof remains required when the schema adapter is supplied.
