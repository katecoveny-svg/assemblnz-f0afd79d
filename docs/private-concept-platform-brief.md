# Private concept platform — strategic brief

Status: locked 2026-07-22. This is the durable spec for assembl's private
outreach concepts (Woolworths, Air New Zealand, Contact). It supersedes
treating each concept as a one-off microsite build.

## 1. The architecture

One shared journey engine. One private editorial structure. One completely
recognisable customer experience per organisation.

The Woolworths, Air New Zealand and Contact concepts should not be rebuilt
as generic assembl dashboards. They should become branded customer-facing
moments within the same verified journey architecture (`lib/journey/`, the
`CustomerJourney` object — see `docs/agentic-customer-journey.md`).

This moves assembl from speculative design work toward forward-deployed
agentic customer-experience strategy. The existing microsites say "here is
an exciting product idea." This format says "here is a specific customer
journey, the working experience it creates, the system operating
underneath it, the business result we would test, and the smallest
credible way to pilot it."

### Four non-negotiable additions

**1. Preserve before replacing.** Before modifying any existing concept,
capture its current route, screenshots, copy, responsive behaviour,
animations and reusable components. Preserve the strongest implementation
rather than recreating it approximately. (Tracked as
`docs/concept-visual-inventory.md`.)

**2. Separate configuration from bespoke presentation.** Not every screen
should be generated by one generic component. The editorial frame, runtime,
proof and verification are shared; each organisation gets a genuinely
custom signature experience:

```
shared                              tenant-specific
private arrival                     signature visual moment
journey map                         brand-adapted interaction
runtime state                       customer scenario
inside-the-journey                  micro-animation
verification                        industry language
proof
commercial model
pilot
disclosures
```

Do not force all three signature demos into identical card structures.

**3. One shared run ID across both views.** The customer experience and
the inside-the-journey view must consume the same journey run ID, event
stream, scenario state, approvals and ProofMetrics. Changing a scenario
input in either view must update both representations consistently. This
is what makes the credibility layer genuine, not two separate mock states.

**4. Protect the microsites appropriately.** These concepts are valuable
outbound sales assets. "Unlisted" URLs alone are not meaningfully private.
For flagship targets, use named private routes, organisation-specific
access tokens (magic links), `noindex`, no sitemap inclusion, no public
tenant directory, expiry/revocation support, and clear independent-concept
disclosure.

### Build sequence

Do not build all three fully in parallel.

```
shared private renderer
  → Woolworths complete golden journey
  → validate shared architecture
  → Air New Zealand adaptation
  → Contact adaptation
```

Woolworths proves: natural-language input, context assembly, plan and
basket, budget resolution, approval, productive wait state, proof.

Air New Zealand then proves the architecture supports a very different
journey: passenger state, disruption/wait detection, useful intervention,
reward/partner moment, onward action, proof.

Contact proves it can handle a service and account relationship: household
context, usage/billing concern, recommendation, approval, action
preparation, service resolution, retention/support proof.

Once those three work through one renderer, this is genuinely a reusable
private-concept platform, not three bespoke builds.

## 2. The experience concepts

Current CX direction is moving toward journey-based resolution, embedded
AI rather than separate chat windows, persistent context, real-time
orchestration and measurable outcomes. Retail and travel assistants are
increasingly collapsing planning, comparison and action into one flow,
while production-grade systems are judged on traceability and reliability
rather than model cleverness alone.

Fourteen concepts were proposed. Each is described generically, then per
brand where the brief gave brand-specific detail.

1. **The "change one thing" moment.** One beautifully presented executive
   control that changes what happens (extra guest, budget drop, dietary
   change, cancelled dinner, stockout for Woolworths; delay, child
   traveller, full lounge, tight connection, declined offer for Air New
   Zealand; house move, bill spike, outage, solar/EV context for Contact).
   The full experience visibly reassembles: `household changed → plan
   reconsidered → basket rebalanced → budget restored → approval updated →
   proof recalculated`. The single most valuable wow factor — it proves
   the system is dynamic, not a polished slideshow.

2. **A "journey director's cut."** Replay the journey as a premium
   horizontal cinematic timeline (not logs, not developer code) —
   timestamped events, each expandable to show what changed, which agent
   acted, what evidence it used, why approval was/wasn't required, and
   what metric moved. Titled "How this journey assembled."

3. **Before assembl / with assembl.** The original fragmented journey
   (e.g. nine steps: open app, search products, check calendar, message
   family, calculate meals, compare total, remove items, check rewards,
   confirm order) beside the assembled version (describe the week, review
   the prepared plan, approve). Animate the collapse. Show taps removed,
   systems crossed, questions repeated, customer minutes, avoidable
   service contacts, uncompleted steps.

4. **The counterfactual view.** "What would have happened without
   intervention?" — clearly labelled as simulated/modelled, never measured
   truth. Shows why the agent intervened (e.g. basket would exceed budget
   by $31; passenger waits without knowing the next step).

5. **Agent negotiation made visible.** Specialist agents (basket, budget,
   preference, resolution) briefly resolving a conflict as a beautifully
   designed decision table, with the final resolution assembling in the
   centre — not agents "chatting recreationally." Communicates why
   specialist agents beat one generic assistant.

6. **An executive control room ("what you could control").** Let the
   recipient alter business rules (max discount, reward budget, escalation
   threshold, approval authority, acceptable basket variance, partner
   category, tone, vulnerable-customer rule, autonomy level), then rerun
   the same journey and watch the projected volume/hypothesis update.

7. **A customer memory passport.** Shows the journey remembering only
   useful, permissioned context (e.g. "usual household: 4, pescatarian
   guest: Mila, weekday preference: low preparation"). Each memory item
   can be viewed, corrected, made one-time-only, removed, or prevented
   from being stored. "Personalisation you can see and control."

8. **Cross-surface continuity.** A journey that begins on one surface and
   moves naturally to another (voice note → app → approval notification →
   household shared view → operator proof), showing assembl carrying
   context across surfaces rather than forcing everything into one chat
   window.

9. **One real live signal in every flagship demo.** Even when most of the
   concept is simulated, connect one genuinely live data source (e.g.
   current Auckland weather, a real public flight-status feed), clearly
   labelled `live signal` vs `illustrative context` vs `assembl response`.
   Dramatically increases believability without full enterprise
   integration.

10. **The journey constellation.** A quiet spatial composition — customer
    at the centre, journey stages as large editorial nodes, specialist
    agents assembling around the active stage, Business Genome rules
    arriving as small silver fragments, approvals as a visible threshold,
    proof gathering behind the completed journey. Physically reorganises
    as the scenario changes. Real-time, derived from journey state — not
    a background video. Used sparingly: hero reveal, transition into
    inside-the-journey, final replay.

11. **A commercial hypothesis that changes live.** As the journey changes,
    the commercial opportunity updates (e.g. "customer intervention added:
    budget rescue → possible effects: + basket completion, + customer
    trust, − abandonment → pilot measures added: budget-exception recovery
    rate, approved substitution rate, repeat use within 30 days").
    Demonstrates assembl designs testable commercial systems, not just
    screens.

12. **"Ask this journey anything."** After the run, let the executive
    question the completed journey (why recommend this, what needs
    integration, least certain assumptions, failure behaviour, what data
    was used, pilot-first candidate, operating cost, where a human still
    intervenes). Answers grounded in the actual run, capability registry,
    agent contracts, disclosures, commercial hypothesis and pilot proposal
    — not a general website chatbot.

13. **The "human rescue" moment.** One graceful human handoff, packaging
    customer goal, known context, steps completed, unresolved issue,
    recommended next action, supporting evidence, customer sentiment —
    "Ready for Hannah in the service team — without asking the customer to
    repeat anything." Proves assembl values resolution over autonomy.

14. **A pilot simulator.** Configure the smallest credible pilot (eligible
    customers, journey type, duration, autonomy, data source, approval,
    primary measure). assembl generates proposed scope, required
    integrations, agent authority, test scenarios, pilot measures,
    operating risks, indicative timeline, hypothesis to validate. Terminal
    action: "Save this pilot architecture" (draft-only) rather than
    "Contact us" — a strong lead signal.

### The five to build first

Not all fourteen at once. The strongest initial combination:

1. Change one thing — dynamic scenario recomputation.
2. How this journey assembled — cinematic evidence replay.
3. Before / with assembl — instant executive value.
4. Agent negotiation — proves specialist orchestration.
5. Pilot simulator — converts fascination into a concrete next step.

Reveal sequence, Woolworths (built first):

```
describe the week
→ watch household context assemble
→ see the prepared shop
→ unexpectedly add two teenagers
→ basket and budget reassemble live
→ inspect the agent negotiation
→ compare manual actions with approvals
→ configure a six-week pilot
```

Reveal sequence, Air New Zealand (later, reusing the same renderer):

```
normal travel day
→ disruption occurs live
→ journey reorganises
→ passenger uncertainty falls
→ useful wait option appears
→ passenger rejects an irrelevant offer
→ system adapts without repeating it
→ commercial model updates
→ pilot configured
```

Reveal sequence, Contact (later, reusing the same renderer):

```
unexpected bill
→ weather and household context assemble
→ likely drivers explained
→ recommended actions ranked
→ vulnerable-customer safeguard activates
→ human handoff prepared
→ avoided service effort and retention hypothesis shown
```

## 3. What's being built now

Per the build sequence above: the shared private renderer + access control,
then the five priority features on the Woolworths golden path only. Air New
Zealand and Contact adopt the same renderer in a later pass, once the
shared architecture is validated. Every simulated/counterfactual/modelled
element is labelled as such; nothing sends, books or pays without a human
yes, consistent with assembl's product principles.
