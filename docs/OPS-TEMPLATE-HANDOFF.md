# Ops-dashboard template — handoff

The ops-dashboard template is the shared branded surface every customer's ops team lands on. It lives at `/customers/[slug]/ops/*` and is built from three layers: a Zod-validated brand config, a themed shell, and a set of brand-aware widgets. Everything else — page composition, wired data, custom scenes — is per-customer.

## Adding a new customer

Adding a new customer takes three files and no code changes anywhere else. Start with `lib/brand/brand-config.ts` and read the `BrandConfig` schema so you know exactly which fields matter. Create a new file at `lib/brand/configs/<slug>.ts` that exports a `BrandConfig` validated through `parseBrandConfig`. Register it in `lib/brand/configs/index.ts` by adding the slug to the `brandConfigs` record. If the customer needs a bespoke hero, add the scene to the `Hero3DSceneId` enum in `brand-config.ts`, drop the scene component under `components/ops/hero3d/`, and wire it into `components/ops/Brand3DCanvas.tsx`. If the customer is happy with one of the existing six heroes, skip that step and reuse one. Google fonts wire through `lib/brand/fonts.ts` — if your customer's font isn't there yet, add a `next/font/google` loader and a switch case; other brands are unaffected. Once the config is in place, `/customers/<slug>/ops` renders automatically.

## Widget reuse vs extend

The default widget set covers the common ops surfaces — roster, CRM, comms drafts, finance summary, compliance calendar, upcoming events, loyalty state, and the mana receipt viewer. If the shape of a customer's data is a subset or superset of the shared types in `components/ops/widgets/types.ts`, reuse the widget by adapting the data at the page level and passing it in. If the shape genuinely diverges — an aviation ops team needs turnaround times, not a groomer roster — copy the widget into `components/customers/<slug>/` and extend from there rather than making the shared widget grow options. The shared widgets read colours only through the `--brand-*` CSS variables, so they inherit any brand config automatically; do not put hex codes in shared widgets. Hero scenes are allowed to hardcode hex because they are brand-owned art, not reusable UI.

## Motion budget

The template holds itself to a strict motion budget so ops surfaces feel calm rather than performative. Any widget may run at most two concurrent animations at a time, and the 3D hero targets 30 fps by capping `dpr` to `[1, 1.5]` in `Brand3DCanvas`. All motion primitives in `lib/motion` respect `prefers-reduced-motion` — when the user asks for less motion, `FadeIn` and `SlideUp` render the final state immediately, `HoverLift` becomes a no-op, and `TickerNumber` snaps to the new value without a spring. The 3D hero itself is replaced by `StaticFallback` (a brand-tinted SVG) under reduced motion. Do not add global CSS animations or looping keyframe backgrounds; they escape the budget and clash with the widget-level primitives.

## `OpsShell` slot API

`OpsShell` (`components/ops/OpsShell.tsx`) is the reusable chrome around every ops surface. It expects a validated `BrandConfig` and renders the header, sidebar navigation, a greeting bar sourced from `config.voice.greeting`, the main content area, an optional `rightRail` slot, and the footer lockup whose density is driven by `config.crossBrand.density`. Pass `rightRail` as a `ReactNode` to fill the third column — the default `[slug]/ops/layout.tsx` populates it with a `<ManaReceiptViewer>`, a diary placeholder, and an alerts placeholder, all tagged `demo`. The shell itself wraps children in `<BrandThemeProvider>`, so any widget deeper in the tree can call `useBrandTheme()` for the current config and CSS variables without prop-drilling. If a customer needs a completely different chrome — a kiosk-style single-widget surface, say — build it as a sibling of `OpsShell` rather than adding options, and keep it in the shared `components/ops/` folder so future customers can adopt it.
