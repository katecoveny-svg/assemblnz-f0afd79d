# Owner-only activation plan — revised V2, unapplied

The canonical staged route is `/studio/workspace`, private/noindex, with `/api/client-hub-migration/owner`. Existing `/studios`, original Site, records and links remain untouched. Stage1 creates new empty drafts only; no legacy import is necessary for this limited route.

The owner can edit company/client/brief, manually author an idea, edit its story/options, use the original interactive renderer and save/reopen. The owner view starts at Client brief with step navigation and one relevant visual panel. Promotional heroes/outcomes and unconnected toolbar actions are omitted only in owner mode. Inline branding remains part of the draft; company-wide deck/media storage, research, generation, agent execution and sharing are unavailable. No provider calls or paid generation occur on mount.

## Before enabling anything

1. Obtain independent re-review of `owner-schema-proposal.sql`, its generated full contract and tests. V1 was rejected and is archived solely as history. The revised proposal is not in production migrations and has not been applied to a linked project. Recipient/Storage work is explicitly excluded; `storage-policy-proposal.sql` is comments only.
2. Verify the production extension namespace/version, trusted migration/function owner and actual existing grants. Local tests use the Supabase Postgres17.6.1.139 image, not the production project's metadata. Install through the approved migration workflow only after targeted approval.
3. Operator seed exactly the approved existing auth user into `studio_owner_access`, enabled only when approved. Clients have SELECT only and cannot insert/update/delete this table. This DB row is the authoritative enablement boundary for direct RPC/RLS access. The server flag and exact UUID environment allowlist are additional UI/API gates, not substitutes for DB enablement. Never seed from display names, client choices, user metadata or request payload.
4. Existing cookie client plus `auth.getUser()` verifies the owner, rejects anonymous users and checks an enabled visible DB row. No service-role identity bypass or copied credentials. API requests use private/no-store, same-origin writes, a streamed1.8MB body cap and the original Zod contract.
5. Owner tables expose no direct INSERT/UPDATE/DELETE/TRUNCATE privileges. Narrow security-definer save/delete RPCs have fixed empty search paths, verified non-anonymous caller identity, explicit required-argument validation and owner-scoped expected-revision CAS. Their trusted operator ownership must be reviewed. PUBLIC and named client-role grants are explicitly revoked before limited SELECT/EXECUTE grants.
6. Full DB payload validation uses pg_jsonschema plus version/type/byte checks and the original contract's URL/logo, colour contrast, Cinema and Radar refinements. DB validation is intentionally stricter for unknown nested keys, unbounded original date labels and credential-bearing URLs. Normal writes use the app's parsed/normalised original contract. Schema generation is reproducible; do not hand-edit embedded JSON.
7. Per-owner access-row locks serialise every writer/purger. Default quota is20 drafts/20MiB, operator-configurable within bounded ranges. Stored JSONB bytes count; tombstones count until purge. Quotas cover concurrent saves and revisions, rather than trusting a browser count.
8. Soft deletion requires owner identity and expected revision, increments revision and hides the draft from RLS/API reads. Delete RPC exists; no destructive UI action or DELETE HTTP endpoint is exposed in this stage. Default tombstone retention is30 days, configurable1–90. Operator-only purge affects due tombstones only; no cron job is created by this proposal. Agree a monitored purge schedule, disclosure/retention policy and actual backup expiry before activation. Active drafts remain until deletion; auth-user deletion cascades these new owner records only. No original records are touched.
9. After schema and coordinated release approval, prove Kate's actual account: empty start → edits/manual idea → save → reload/reopen → conflict → DB disablement → another synthetic account denied. Existing mocked API tests and isolated SQL do not prove production cookies/JWT, PostgREST or account persistence.

## Rollback and remaining separation

Disable the DB enablement row(s) as well as the server flag. Flag-off alone blocks the UI/API but does not revoke a previously enabled owner's direct RPC access. Preserve drafts, original Site and backups; no deletion/cutover/import is part of rollback.

Recipient API stays404/no-store. No grants, invitations, uploads, Storage policies, public links, paid provider connections or old-data transfers are activated. A future recipient/media proposal requires its own bounded forbidden-field-safe projection, snapshot/revision-bound media, owned namespaces and existing bucket-policy audit. Already issued signed URLs remain usable until their expiry unless the serving system supports additional revocation; do not promise immediate revocation.
